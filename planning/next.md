## v0.5: Analyst portfolio *(now)*

Strategic context: [`roadmap.md`](roadmap.md) → *v0.5*. The v0.4 on-ramp moves an analyst's published work in; v0.5 makes that body of work a first-class object: a profile that stands as a portfolio, link previews that render the work wherever a URL lands, a completion flow that prices publishing an import at one decision instead of one form per draft, and source archival that makes every event outlive its source tweet, drafts included. Read stays open, write stays invite-gated.

**Decision: open write moves to v1.0.** The former open-beta packaging of this version is redistributed: self-registration, its anti-abuse stack, and the auth-hardening tiers land with the public switch (v1.0); upload moderation is v0.7; handle ownership + disputes are v1.0. Invite codes stay the only write door until v1.0. The anti-scraping floor still ships here: read has been public since v0.4 and doesn't wait for open write.

| Pri | Area | Item | Why / how |
|---|---|---|---|
| P0 | Portfolio | OG share cards for profiles + event pages | When a profile or event URL lands on X / Discord, the preview renders the work: title, coordinates, a mini-map, the analyst's handle and counts. `next/og` runtime image generation; the data already travels in the page payloads. |
| P0 | Portfolio | Profile portfolio pass | The public profile becomes the analyst's landing page: insights lead (the `GET /users/{username}/stats` section shipped in v0.4), add a per-analyst map of their geolocations and a copy-link share affordance. The bar: the page holds up as the link an analyst pins in their X bio. |
| P0 | Portfolio | Batch completion + publish flow on drafts | The `detected → geolocated` step is where imported work stalls, and per-draft one-click publish is not achievable: the floor requires judgment the machine can't supply, one conflict + one `capture_source` tag ([`events.py::_require_submission_floor`](../backend/app/services/events.py)) plus a proof image. The honest shape is the batch: select N drafts, set the conflict once (an import is usually dominated by one conflict), pick the capture source per row from a dropdown in the completion table (drone, ground, satellite, CCTV vary draft to draft, with an optional apply-to-all for the imports where they don't), publish the lot, per-row floor errors. The economics survive because the import already filled title, coordinates, source, and proof, so the per-draft cost falls to one dropdown click instead of a full form. The proof-image leg is already satisfied when the thread carried annotation media (`proof_media`); the flow surfaces the rows where it isn't. A digest email lists drafts awaiting completion. Optional assist, suggested never auto-applied: infer the likely conflict from nearby catalog events. |
| P0 | Archival | Automated source archival (Wayback Machine / archive.today) at event creation | Source tweets get deleted and accounts suspended, which destroys exactly the work the platform promises to preserve. Archive at creation for **every** event whatever its status, detected drafts included: a draft can wait weeks before publication and its source tweet can die in the interval. Scope: the `source_url` of every event plus the links inside proof bodies (extract the hrefs from the Tiptap JSON in the same pass); analyst profile external links are out of scope (identity, not evidence). Plus a backfill over the existing catalog. Queued behind the durable worker with retry and backoff (the archive services rate-limit); the archived URL needs a home on the event and is rendered as a fallback link once the source dies. `event_source_links` (shipped, holds an event's ordered secondary mirrors) is a candidate home for it, extended with a kind/type discriminator to tell an archived-copy row from an analyst-submitted mirror. Promoted from *Future considerations*. |
| P1 | UX | Mobile pass on the shared surfaces (profile, event detail) | Links shared on X are mostly opened on phones; the two pages the share cards point at must hold up under 375px. The full golden-path mobile audit stays at v1.0. |
| P0 | Anti-scraping | `?bbox=` required on `/events/points` + viewport-driven map fetch | Catalog size stops mattering, viewport size matters instead. Kills the dominant Phase-3 cost line + the "one curl loads the catalog" vector. PostGIS `ST_MakeEnvelope` + MapLibre viewport listener. ~2 days. |
| P0 | Anti-scraping | Hard server-side `LIMIT 100` on every list endpoint + `Link: rel="next"` cursor | Single biggest other scraping mitigation. Validate `limit`/`page` params in the same pass; garbage values 500 today instead of 422, and one list endpoint hydrates unbounded. |
| P0 | Anti-scraping | Per-user limit on authenticated reads (~1000 req/hr) | Logged-in scraper rotating IPs still hits a wall. Keyed by `User.id`. |
| P0 | Anti-scraping | Behavioral tests on every documented write limit | The read surface is pinned per documented limit and the wiring has its own coverage ([`test_rate_limits.py`](../backend/tests/test_rate_limits.py)), but the write / auth / admin limits don't: dropping a `@limiter.limit` on a specific write endpoint still passes CI green. One parametrized test per remaining documented limit: N requests pass, N+1 returns 429. |

## v0.6: Collaboration & reviews

Strategic context: [`roadmap.md`](roadmap.md) → *v0.6*. Two phases on top of the v0.5 primitives (dedup creates the encounters between analysts). **A**, the substrate: notifications as the connective tissue, shared credit on events, edit history on a published geolocation, and the request board as a collaborative queue. **B**, the visible layer it carries: organizations as a first-class entity, and a review layer where an analyst or an organization approves a published geolocation at a specific revision. B needs A: revisions are what an approval binds to, and notifications carry the re-review loop. The shipped verdict is a single approve, deliberately: ship the simple gesture, see whether it takes, and let richer verdicts follow the usage rather than precede it (analysis in prose is what the deferred comments surface would be, see [`roadmap.md`](roadmap.md) → *Future considerations*). Bounded by the cross-cutting rule below: a review is attestation, never a score.

| Pri | Area | Item | Why / how |
|---|---|---|---|
| P0 | Notifications | A: `/notifications` feed + sidebar unread binding | The connective tissue for everything else in the version: geolocator additions, follows, fulfilled requests, and the phase-B review events have to land somewhere felt. Last-read marker per user + `> last_read` count binds the sidebar `notify` dot. |
| P0 | Collaboration | A: Geolocator-addition model + flow | The event-model refactor landed the `event_geolocators` table (who vouched the location) but no write path: only the submitter of a `geolocated` event is a geolocator. Decide **how a second geolocator joins an event**, self-add (free), request-and-accept (owner approves), or owner-invite, then build it. Interacts with the `event_investigators` ("working on it") signal (an investigator who lands the location becomes a geolocator). Lean request-and-accept as the default so write access can't be abused to hijack attribution. |
| P0 | Collaboration | A: Re-home attribution reads onto `event_geolocators` | The refactor keeps the single-author read surfaces on `owner_id` (profile "my geolocations" count/list, the detail/card byline, search-by-author all read the one owner). Once multi-geolocator write exists (row above), re-home them: profile geolocations = `event_geolocators` membership, byline = the contributor set, search-by-author = "any credited geolocator matches". Needs `selectinload` on the geolocator→user set to avoid N+1 and a `(user_id, created_at)` index for the reverse profile query. |
| P0 | History | A: Event revision model + edit-with-history | Input errors happen and a correction must not silently rewrite the record. An append-only revisions table snapshots the structured fields (title, event coordinates, capture-source coordinates, event date, proof body, tags, conflicts) on every edit of a geolocated event. The current edit flow ([`EventEditForm.tsx`](../frontend/src/components/geolocations/edit/EventEditForm.tsx) against the event update service) writes a revision instead of overwriting silently. **Editability contract:** after publication the evidence anchor is immutable, so `source_url` and the source media cannot be edited (a wrong source is handled by close and repost, or by admin action). Secondary source links (`event_source_links`) sit outside that anchor and stay editable; this immutability doesn't reach them. Everything else is editable and revisioned: title, both coordinate sets, event date, tags, conflicts, proof body, and the proof media set. Media files themselves are not versioned, but a media row referenced by a past revision is never hard-deleted while it is referenced, so history stays renderable. The revision is also what a phase-B review binds to. |
| P1 | History | A: Version history read surface | The event page exposes the revision list (who edited, when, what changed); the current version stays the canonical render, prior versions are readable next to it. |
| P1 | UX | A: Clickable analyst handles everywhere (cards, timeline, search hits) | Each handle links to `/search?author=<handle>` (the filter shipped in v0.4; the profile "Show more" is the first entry point). |
| P1 | Requests | A: Notifications when a request you're investigating is fulfilled by someone else | Collaborative-queue courtesy. Rides the `/notifications` feed above. |
| P1 | Requests | A: Enrich the Requests board into a triage surface | Today it is the flat list of open requests (newest first, no status filter, deliberately thin at closed-beta volume). Add sort (newest · oldest-open · most-worked), filters (conflict · capture source · unclaimed vs being-worked-on · coordinate-guess vs blind), and per-card signals (open for N days, `investigator_count`). Reuses the map/search filter set; interacts with the `event_investigators` "working on it" signal. |
| P2 | Requests | A: Investigate-signal TTL (7 days) + reaper | Once `event_investigators` rows accumulate past what's still relevant. |
| P2 | Requests | A: Request owner marks a specific investigator's geolocate as "the answer" | Deferred until queue ambiguity matters. |
| P2 | Timeline | A: Requests in the feed | Mixed ordering by `created_at desc`. |
| P2 | Timeline | A: Cursor pagination + infinite scroll | OFFSET stops scaling. |
| P2 | Timeline | A: Scope toggle (`Following` / `All`) | Opt-out from empty followed-set. |
| P0 | Organizations | B: Organization entity + verified creation | Model: name, avatar, bio, links, plus an `x_handle` identity anchor like analyst accounts carry. Creation is admin-only while the community is small, which keeps a name from being squatted and doubles as manual verification of that handle. Public org profile page listing its members and its reviews. |
| P0 | Organizations | B: Membership + roles | Exactly two roles, org-admin and member. Entry is by org-admin invitation only. No hierarchy and no permission matrix: the single thing the role gates is acting in the organization's name. |
| P0 | Reviews | B: Review model bound to a revision | The shipped verdict is a single **approve**: a dated attestation bound to one revision, placed by a user or an organization (acting member recorded), with an optional note. The model keeps a verdict field internally so richer verdicts can land later without a migration; the UI exposes approve only. Revocation is transparent: revoking requires a reason and keeps the review readable in history with the interval it stood (placed at X, revoked at Y), never a silent delete. |
| P0 | Reviews | B: Review write flow + event-page render | An approve action on a geolocated event's page. Reviews render only on the revision they cover: when a new revision lands, the current version shows no reviews until it is approved again, and the prior approvals stay readable in the revision history. |
| P0 | Reviews | B: Re-review loop | A new revision notifies each reviewer of the prior revision (rides the phase-A notifications feed). Re-approving is one action. |
| P1 | Reviews | B: Review requests | An analyst asks a named analyst or organization to approve an event; it lands in the target's notifications, and open requests are visible on the event page. |
| P1 | Reviews | B: Org review governance | Which members may place the org approval (org-admin only at first), with the acting member always recorded and visible. |
| P2 | Reviews | B: Perceptual near-duplicate media matching | Beyond exact `sha256`: perceptual hashing surfaces re-encoded / cropped re-uploads of the same footage across analysts. It lands here because the review layer is what consumes the encounter: the match tells an analyst or an organization there is a geolocation to review. Also feeds the bot reply (another analyst already covered the scene). |
| P2 | Reviews | B: Reviewed-by read filter | Filter map / search by "reviewed by X", once review volume justifies it. |

## v0.7: Moderation

**Cross-cutting rules:**

- **Recognition never becomes a quality signal.** Scores, badges and streaks never gate or rank content. The platform's quality model rests on per-event attestation (the review layer) + per-action moderation, not reputation math (see [`roadmap.md`](roadmap.md) → *Future considerations → Trust + governance*).
- **Reviews are attestation, not a score.** A review never changes an event's status and never aggregates into a score. The platform renders who reviewed what at which revision, nothing more; readers weigh the reviewers themselves.
- **Backup hardening is pick-up-reactively.** The quarterly drill stays the canonical "is the backup real" check; deviation from the current weekly cron only when one of the rows above hits a concrete trigger.
