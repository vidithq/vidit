# What's next

Work tracker organized by the version milestones defined in [`roadmap.md`](roadmap.md). Items get deleted when they ship; the [CHANGELOG](../CHANGELOG.md) records what landed.

Within each version, rows carry a priority:

- **P0**: hard blocker; the version doesn't ship without it.
- **P1**: strongly recommended; lands inside the version if there's time.
- **P2**: nice-to-have; can slip without embarrassment.

The [Refactors](#refactors) at the bottom are ongoing engineering hygiene, not gated on any version.

## v0.6: Collaboration & reviews *(now)*

Strategic context: [`roadmap.md`](roadmap.md) → *v0.6*. Two phases on top of the v0.5 primitives (dedup creates the encounters between analysts). **A**, the substrate: notifications as the connective tissue, shared credit on events, edit history on a published geolocation, and the request board as a collaborative queue. **B**, the visible layer it carries: organizations as a first-class entity, and a review layer where an analyst or an organization approves a published geolocation at a specific revision. B needs A: revisions are what an approval binds to, and notifications carry the re-review loop. The shipped verdict is a single approve, deliberately: ship the simple gesture, see whether it takes, and let richer verdicts follow the usage rather than precede it (analysis in prose is what the deferred comments surface would be, see [`roadmap.md`](roadmap.md) → *Future considerations*). Bounded by the cross-cutting rule below: a review is attestation, never a score.

| Pri | Area | Item | Why / how |
|---|---|---|---|
| P0 | Notifications | A: `/notifications` feed + sidebar unread binding | The connective tissue for everything else in the version: geolocator additions, follows, fulfilled requests, and the phase-B review events have to land somewhere felt. Last-read marker per user + `> last_read` count binds the sidebar `notify` dot. |
| P0 | Collaboration | A: Geolocator-addition model + flow | The event-model refactor landed the `event_geolocators` table (who vouched the location) but no write path: only the submitter of a `geolocated` event is a geolocator. Decide **how a second geolocator joins an event**, self-add (free), request-and-accept (owner approves), or owner-invite, then build it. Lean request-and-accept as the default so write access can't be abused to hijack attribution. |
| P0 | Collaboration | A: Re-home attribution reads onto `event_geolocators` | The refactor keeps the single-author read surfaces on `owner_id` (profile "my geolocations" count/list, the detail/card byline, search-by-author all read the one owner). Once multi-geolocator write exists (row above), re-home them: profile geolocations = `event_geolocators` membership, byline = the contributor set, search-by-author = "any credited geolocator matches". Needs `selectinload` on the geolocator→user set to avoid N+1 and a `(user_id, created_at)` index for the reverse profile query. |
| P0 | History | A: Event revision model + edit-with-history | Input errors happen and a correction must not silently rewrite the record. An append-only revisions table snapshots the structured fields (title, event coordinates, capture-source coordinates, event date, proof body, tags, conflicts) on every edit of a geolocated event. The current edit flow ([`EventEditForm.tsx`](../frontend/src/components/geolocations/edit/EventEditForm.tsx) against the event update service) writes a revision instead of overwriting silently. **Editability contract:** after publication the evidence anchor is immutable, so `source_url` and the source media cannot be edited (a wrong source is handled by close and repost, or by admin action). Secondary source links (`event_source_links`) sit outside that anchor and stay editable; this immutability doesn't reach them. Everything else is editable and revisioned: title, both coordinate sets, event date, tags, conflicts, proof body, and the proof media set. Media files themselves are not versioned, but a media row referenced by a past revision is never hard-deleted while it is referenced, so history stays renderable. The revision is also what a phase-B review binds to. |
| P1 | History | A: Version history read surface | The event page exposes the revision list (who edited, when, what changed); the current version stays the canonical render, prior versions are readable next to it. |
| P1 | UX | A: Clickable analyst handles everywhere (cards, timeline, search hits) | Each handle links to `/search?author=<handle>` (the filter shipped in v0.4; the profile "Show more" is the first entry point). |
| P1 | Requests | A: Notifications when a request you opened is fulfilled | Collaborative-queue courtesy. Rides the `/notifications` feed above. |
| P1 | Requests | A: Enrich the Requests board into a triage surface | Today it is the flat list of open requests (newest first, no status filter, deliberately thin at beta volume). Add sort (newest · oldest-open), filters (conflict · capture source · coordinate-guess vs blind), and per-card signals (open for N days). Reuses the map/search filter set. |
| P2 | Requests | A: Request owner marks a specific fulfiller's geolocate as "the answer" | Deferred until queue ambiguity matters. |
| P2 | Timeline | A: Requests in the feed | Mixed ordering by `created_at desc`. |
| P2 | Timeline | A: Cursor pagination + infinite scroll | OFFSET stops scaling. |
| P2 | Timeline | A: Scope toggle (`Following` / `All`) | Opt-out from empty followed-set. |
| P0 | Organizations | B: Organization entity + verified creation | Model: name, avatar, bio, links, plus an `x_handle` identity anchor like analyst accounts carry. Creation is admin-only while the community is small, which keeps a name from being squatted and doubles as manual verification of that handle. Public org profile page listing its members and its reviews. |
| P0 | Organizations | B: Membership + roles | Exactly two roles, org-admin and member. Entry is by org-admin invitation only. No hierarchy and no permission matrix: the single thing the role gates is acting in the organization's name. |
| P0 | Reviews | B: Review model bound to a revision | The shipped verdict is a single **approve**: a dated attestation bound to one revision, placed by a user or an organization (acting member recorded), with an optional note. The model keeps a verdict field internally so richer verdicts can land later without a migration; the UI exposes approve only. Revocation is transparent: revoking requires a reason and keeps the review readable in history with the interval it stood (placed at X, revoked at Y), never a silent delete. |
| P0 | Reviews | B: Review write flow + event-page render | An approve action on a geolocated event's page. Reviews render only on the revision they cover: when a new revision lands, the current version shows no reviews until it is approved again, and the prior approvals stay readable in the revision history. |
| P0 | Reviews | B: Re-review loop | A new revision notifies each reviewer of the prior revision (rides the phase-A notifications feed). Re-approving is one action. |
| P1 | Reviews | B: Review requests | An analyst asks a named analyst or organization to approve an event; it lands in the target's notifications, and open requests are visible on the event page. |
| P1 | Reviews | B: Org review governance | Which members may place the org approval (org-admin only at first), with the acting member always recorded and visible. |
| P2 | Reviews | B: Perceptual near-duplicate media matching | Beyond exact `sha256`: perceptual hashing surfaces re-encoded / cropped re-uploads of the same footage across analysts. It lands here because the review layer is what consumes the encounter: the match tells an analyst or an organization there is a geolocation to review. Also feeds the bot reply (another analyst already covered the scene). |
| P2 | Reviews | B: Reviewed-by read filter | Filter map / search by "reviewed by X", once review volume justifies it. |

## v0.7: Moderation

Strategic context: [`roadmap.md`](roadmap.md) → *v0.7*. The moderation pipeline built as product, one version ahead of its legal wrap (v1.0): the community layer (report + queue), the machine layer (upload scanning), and the written policy. Sequenced before open write so the tooling is proven while contributors are still invite-curated. Report and dispute (v0.6) stay two distinct pipes: a dispute is analyst-to-analyst epistemics, public and part of the work; a report is a policy violation, private, landing in the admin queue.

| Pri | Area | Item | Why / how |
|---|---|---|---|
| P0 | Moderation | Polymorphic "Report this" + admin moderation queue | `content_type` + `content_id` so one mechanism covers events, profiles, and whatever content type comes third; queue statuses, actions, and an audit trail in the admin panel; the in-app report flow is the channel, with the Discord link in `BetaBanner` and on `/about` as the informal fallback. Becomes the DSA Article 16 mechanism at v1.0 by legal wrapping (deadlines, acknowledgements, statements of reasons), not rebuilding. **In review on this branch, event-scoped only:** `content_reports` (`event_id` FK, five reasons, never deleted) plus `POST /events/{id}/report` (anonymous allowed), `GET /admin/reports`, `POST /admin/reports/{id}/resolve` (`marked_graphic` \| `hidden` \| `dismissed`), and `PATCH /admin/events/{id}/moderation` for a direct takedown, each verdict appending an `admin_events` row. `content_type` / `content_id` polymorphism (profiles, etc.) is still open. |
| P0 | Moderation | AWS Rekognition pipeline at upload | `DetectModerationLabels` images, `StartContentModeration` async videos. Persist labels on `Media`. |
| P0 | Moderation | CSAM scanning in front of S3 (Cloudflare free tool or PhotoDNA) | Non-negotiable in most jurisdictions. |
| P1 | Moderation | UI sensitive-content gate wired to Rekognition labels | **In review on this branch, author-set rather than Rekognition-driven:** `events.is_graphic`, set by the author on submit / edit and admin-overridable, gates the media behind `GraphicContentGate` (blur + one per-session 18+ confirmation) on every surface that renders it. Wiring the flag to Rekognition labels at upload is still open. |
| P1 | Moderation | Video upload metadata strip | mp4 atom-level and GPS-tagged QuickTime metadata skip today's synchronous strip (images only, see [`evidence_processing.py`](../backend/app/services/evidence_processing.py)). Its trigger is met: the durable worker exists, and async video Rekognition rides the same off-request path, so the ffmpeg pass lands behind the worker in the same build. |
| P1 | Privacy | Decide stored network context (IP / UA) for abuse response | v0.4 dropped all stored IP/UA (privacy-first; Cloudflare holds the edge). Moderation may need per-event network context: either reintroduce it with retention limits + access controls (not raw columns), or record the decision that the edge stays the only place IPs live. |
| P1 | Policy | Public content policy, product draft | What the platform hosts and removes: graphic footage in documentary context, terrorism-content boundaries, copyright, droit à l'image. The avocat pass at v1.0 formalizes it; writing it now is what makes the queue's decisions consistent. |

## v0.8: Search & discovery

Strategic context: [`roadmap.md`](roadmap.md) → *v0.8*. The corpus becomes smarter than the sum of its pins: events that carry their real structure, search that reaches everything the platform stores, discovery across events.

| Pri | Area | Item | Why / how |
|---|---|---|---|
| P1 | Data model | Multi-point events (`event_points` child table) | One event carries one subject coordinate + one optional camera position today. Real footage spans several subject points (a convoy, multiple impacts from one clip, N coordinates detected from one thread), which currently forces one event per point. The proper fix is a child `event_points` table, not more coordinate columns on `events`. |
| P1 | Search | JSONB content search (geolocation + request proof bodies) | Flatten via `jsonb_path_query_array` materialised into a column or trigger. |
| P1 | Search | URL-fragment search (host + path units) | Paste a tweet ID and find the geo. |
| P1 | Discovery | Related-events suggestions on the event page | Spatial + temporal + tag proximity. Promoted from *Future considerations*: map density by now makes manual discovery slow. |
| P2 | Search | Infinite scroll per group | Cursor keyed by `(rank, created_at, id)`. |
| P2 | Search | `'english'` stemming opt-in | DDL one-line swap if "strikes" misses "strike". |
| P2 | UX | Display `capture_source_coords` on the event detail page | The camera position is write-only in the UI today: captured at submit ([`LocationPicker.tsx`](../frontend/src/components/geolocations/new/LocationPicker.tsx)) and edit ([`EventEditForm.tsx`](../frontend/src/components/geolocations/edit/EventEditForm.tsx)), but no read surface renders it ([`EventDetailBody.tsx`](../frontend/src/components/event/EventDetailBody.tsx) shows only `event_coords`). The value already travels in `EventRead`; add a "Camera position" row next to the coordinates row, same `toFixed(6)` rendering. |

**Cross-cutting rules:**

- **Recognition never becomes a quality signal.** Scores, badges and streaks never gate or rank content. The platform's quality model rests on per-event attestation (the review layer) + per-action moderation, not reputation math (see [`roadmap.md`](roadmap.md) → *Future considerations → Trust + governance*).
- **Reviews are attestation, not a score.** A review never changes an event's status and never aggregates into a score. The platform renders who reviewed what at which revision, nothing more; readers weigh the reviewers themselves.
- **Backup hardening is pick-up-reactively.** The quarterly drill stays the canonical "is the backup real" check; deviation from the current daily cron only when one of the rows above hits a concrete trigger.
