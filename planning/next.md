## v0.6: Collaboration & reviews *(now)*

Strategic context: [`roadmap.md`](roadmap.md) → *v0.6*. Two phases on top of the v0.5 primitives (dedup creates the encounters between analysts). **A**, the substrate: notifications as the connective tissue, shared credit on events, edit history on a published geolocation, and the request board as a collaborative queue. **B**, the visible layer it carries: organizations as a first-class entity, and a review layer where an analyst or an organization approves a published geolocation at a specific version. B needs A: versions are what an approval binds to, and notifications carry the re-review loop. The shipped verdict is a single approve, deliberately: ship the simple gesture, see whether it takes, and let richer verdicts follow the usage rather than precede it (analysis in prose is what the deferred comments surface would be, see [`roadmap.md`](roadmap.md) → *Future considerations*). Bounded by the cross-cutting rule below: a review is attestation, never a score.

The moderation pipeline built as product, one version ahead of its legal wrap (v1.0): the community layer (report + queue), the machine layer (upload scanning), and the written policy. Sequenced before open write so the tooling is proven while contributors are still invite-curated. Report and dispute (v0.6) stay two distinct pipes: a dispute is analyst-to-analyst epistemics, public and part of the work; a report is a policy violation, private, landing in the admin queue.

## v0.8: Search & discovery

Strategic context: [`roadmap.md`](roadmap.md) → *v0.8*. The corpus becomes smarter than the sum of its pins: events that carry their real structure, search that reaches everything the platform stores, discovery across events.

| Pri | Area | Item | Why / how |
|---|---|---|---|
| P1 | Data model | Multi-point events (`event_points` child table) | One event carries one subject coordinate + one optional camera position today. Real footage spans several subject points (a convoy, multiple impacts from one clip, N coordinates detected from one thread), which currently forces one event per point. The proper fix is a child `event_points` table, not more coordinate columns on `events`. |
| P1 | Search | Widen full-text search past the title: proof bodies, URL host and path units, and optional English stemming | Same two files throughout, [`services/search.py`](../backend/app/services/search.py) and the GIN migration, and the tsvector expressions have to stay identical between them or the planner falls back to a sequential scan. **Proof bodies:** JSONB content search over geolocation and request proof, flattened via `jsonb_path_query_array` materialised into a column or a trigger. **URL fragments:** host and path units, so pasting a tweet ID finds the geo. **Stemming:** an `'english'` opt-in, a DDL one-line swap if "strikes" misses "strike". |
| P1 | Discovery | One nearby-catalog-events query, two consumers: related-events suggestions and conflict inference in review | Both want the same spatial-proximity query over the catalog. **Related events** on the event page: spatial + temporal + tag proximity, promoted from *Future considerations* because map density by now makes manual discovery slow. **Conflict inference** in review mode: suggest a likely conflict per detection from the catalog events nearest its coordinates, offered as a pre-selection the analyst confirms, never auto-applied. Review mode is the shared edit form, so each detection opens on its own tags and the conflict is picked per detection; an import that sits in one conflict is the case an assist would flatten first. |
| P2 | Search | Infinite scroll per group | Cursor keyed by `(rank, created_at, id)`. |
| P2 | UX | One pass over the event page's coordinate block: camera-position row and icon-only Maps control | Two small edits in the same area of [`EventDetailBody`](../frontend/src/components/event/EventDetailBody.tsx) and [`CoordinateActions`](../frontend/src/components/event/CoordinateActions.tsx). The camera position is write-only in the UI today: captured at submit ([`LocationPicker.tsx`](../frontend/src/components/geolocations/new/LocationPicker.tsx)) and edit ([`EventEditForm.tsx`](../frontend/src/components/geolocations/edit/EventEditForm.tsx)), but no read surface renders it, `EventDetailBody` showing only `event_coords`; the value already travels in `EventRead`, so add a "Camera position" row next to the coordinates row, same `toFixed(6)` rendering. **Cross-cutting rules:**

- **Recognition never becomes a quality signal.** Scores, badges and streaks never gate or rank content. The platform's quality model rests on per-event attestation (the review layer) + per-action moderation, not reputation math (see [`roadmap.md`](roadmap.md) → *Future considerations → Trust + governance*).
- **Reviews are attestation, not a score.** A review never changes an event's status and never aggregates into a score. The platform renders who reviewed what at which version, nothing more; readers weigh the reviewers themselves.
- **Backup hardening is pick-up-reactively.** The quarterly drill stays the canonical "is the backup real" check; deviation from the current daily cron only when one of the rows above hits a concrete trigger.
